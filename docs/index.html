AI agents meet IBM z/OS

What it does

mainframe-mcp-server turns z/OS capabilities into MCP tools an AI agent can call. Instead of typing Zowe CLI commands, you ask in natural language — “why did PAYJOB01 fail?” — and the agent invokes the right tool with validated inputs and structured output.

MCP tool layer

30+ tools for jobs, datasets, USS, operations, CICS, Db2, SMF, security, and intelligence — designed for LLM parsing.

Zowe connectivity

Uses the same z/OSMF REST APIs as Zowe CLI and Zowe Explorer. Not a replacement for IDz or Z Open Editor — a bridge for AI assistants.

stdio by default

IDE launches the server as a local process. JSON-RPC on stdin/stdout; logs on stderr. No MCP HTTP port unless you explicitly enable SSE.

IDE-driven config

No .env file. Connection settings live in your MCP client config (env block). Installers prompt from server.json metadata.

How it's different

This server fills a gap cloud-native MCP tools cannot: governed, structured access to the mainframe for AI workflows.

Features

Organized into core tooling, operational intelligence, optional enterprise integrations, and security controls.

Core

Job listing, status, spool output, JCL submit, dataset & PDS read/search, failure analysis, safety limits on response size.

Operational intelligence

USS tools, investigate_incident, system_health_summary, abend lookup, structured AI-friendly responses, integration test suite.

Optional enterprise integrations

CICS CMCI, Db2 REST catalog, SMF/RMF metrics, RACF audit queries — enabled through configuration when your environment provides them.

Security layer

Read-only by default, tool allow/block lists, dataset & USS boundaries, audit logging, JCL size caps — enforced at the MCP server in addition to RACF.

Per-user identity

PassTicket propagation so RACF sees who asked — not the service account. Plus mTLS client certificates, JWT/APIML (SSO) tokens, and Zowe team config import.

Governed writes

JCL pre-flight scan (IDCAMS DELETE, IEFBR14 DISP deletes, blocked utilities), change-ticket enforcement, change windows, dry-run, and human-in-the-loop approval.

Multi-environment

Named systems — DEV/TEST/UAT/PROD, multiple LPARs — behind one server. Every tool takes an environment argument; each system carries its own credentials and policy, e.g. read-only on PROD.

Policy-as-code & RBAC

One YAML policy file maps roles to tools, dataset/USS patterns, and change-ticket rules; users map to roles per environment. ${env:VAR} keeps secrets out of the file; unmapped users fail closed.

Audit & SIEM

Structured JSON audit records with correlation ids, exported to Splunk HEC, ELK/webhook, or OpenTelemetry. Records are SHA-256 hash-chained — tamper-evident and verifiable.

Data protection

PII, card numbers (Luhn-validated), SSNs, secrets, JWTs, and private keys masked in job output and dataset reads. Classifications add line caps, sampling, and role-gated access.

Setup instructions

Requirements: Node.js 18+, reachable z/OSMF endpoint, valid z/OS credentials (user/password or token).

Option A — Install via npm (recommended)

Published as @notharshhaa/mainframe-mcp-server. Listed on the MCP registry.

  1. Add to your MCP client

    Cursor: ~/.cursor/mcp.json · VS Code: MCP settings · Claude Desktop: claude_desktop_config.json

  2. Paste the server block

    The IDE installer may prompt for values from server.json. Credentials go in the env block — not a .env file.

  3. Restart the IDE and test

    Ask the agent to run verify_zosmf_connection, then list_jobs.

MCP config (stdio · npm · token auth)
{
  "mcpServers": {
    "mainframe": {
      "command": "npx",
      "args": ["-y", "@notharshhaa/mainframe-mcp-server"],
      "env": {
        "ZOSMF_HOST": "your-zosmf-host.internal",
        "ZOSMF_PORT": "443",
        "ZOSMF_TOKEN": "your-zosmf-token",
        "ZOSMF_TOKEN_TYPE": "LTPA2",
        "ZOSMF_REJECT_UNAUTHORIZED": "true",
        "SECURITY_READ_ONLY": "true",
        "SECURITY_AUDIT_LOGGING": "true"
      }
    }
  }
}

Option B — Run from source (VDI / internal Artifactory)

For environments that block public npm — clone the repo, install dependencies from your internal registry, build locally.

git clone https://github.com/NotHarshhaa/mainframe-mcp-server.git
cd mainframe-mcp-server
npm ci          # against your internal JFrog/npm mirror
npm run build
npm test          # unit tests, no mainframe required
MCP config (stdio · local build)
{
  "mcpServers": {
    "mainframe": {
      "command": "node",
      "args": ["/absolute/path/to/mainframe-mcp-server/dist/index.js"],
      "env": {
        "ZOSMF_HOST": "your-zosmf-host.internal",
        "ZOSMF_PORT": "443",
        "ZOSMF_TOKEN": "your-zosmf-token",
        "ZOSMF_TOKEN_TYPE": "LTPA2"
      }
    }
  }
}
Do not set MCP_TRANSPORT=sse if your organization requires stdio-only MCP. Omit MCP_TRANSPORT entirely — stdio is the default.

Enterprise deployment

Security and governance enforced at the MCP server layer — in addition to RACF and z/OSMF permissions.

Per-user identity — RACF sees who asked

Four mechanisms replace the shared service account. CICS and Db2 REST calls keep the service identity; z/OSMF tool calls run as the end user.

Swipe horizontally to see all columns →

MechanismSetupNotes
PassTicket propagationZOSMF_USER_ID · ZOSMF_PASSTICKET_APPServer generates z/OSMF PassTickets for the end user; every z/OSMF call runs under that identity. 8-minute cache, auto-renewed. Requires PTKTDATA setup.
mTLS client certificateZOSMF_CERT · ZOSMF_CERT_KEYPEM files; pairs with RACF IDID certificate-to-user mapping.
JWT / APIML (SSO)ZOSMF_TOKEN_TYPE=APIML or JWTSent as Authorization: Bearer. Issue via your IdP/gateway; inject with ZOSMF_TOKEN_FILE for refreshable vault tokens.
Zowe team config importZOWE_TEAM_CONFIG · ZOSMF_PROFILEReuse existing Zowe profiles; @secure values honored when stored in the file. Env vars always win.

Governed writes

Every gate is independent and operator-controlled — the agent cannot turn any of them off.

Swipe horizontally to see all columns →

GateVariablePurpose
Read-only modeSECURITY_READ_ONLY=trueBlocks submit_jcl, approve_write, and write tools (default true)
Pre-flight JCL scanSECURITY_JCL_SCAN=trueBlocks IDCAMS DELETE, IEFBR14 DISP=(…,DELETE), blocked utilities, restricted classes (default on)
Blocked programs / classesSECURITY_BLOCKED_PROGRAMS · SECURITY_BLOCKED_JOB_CLASSESExtend the deny list (ADRDSSU, ICKDSF, IEHINITT built in)
Change ticketSECURITY_CHANGE_TICKET_PATTERNWrites must carry a matching ticket ID, e.g. CHG[0-9]{6}
Change windowSECURITY_WRITE_WINDOW + days + timezoneNo PROD submits outside approved hours (overnight windows supported)
Human approvalSECURITY_WRITE_APPROVAL=truesubmit_jcl returns a one-time token; approve_write executes after human review
Tool allowlistSECURITY_ALLOWED_TOOLSLeast-privilege tool access
Tool blocklistSECURITY_BLOCKED_TOOLSExplicitly deny tools
Dataset boundariesSECURITY_ALLOWED_DATASET_PATTERNSRestrict HLQ patterns

Dry-run: submit_jcl({ dryRun: true }) runs structure checks and the pre-flight scan and reports exactly what a real submission would do — without enforcing gates and without touching JES.

Multi-environment, policy-as-code & RBAC, audit & SIEM, data protection

Four scale-up capabilities layer on top of the controls above — env-var rules always apply, and the policy file can only narrow them. Full guide: enterprise.md · worked example: policy.example.yaml

Swipe horizontally to see all columns →

CapabilitySetupWhat you get
Multi-environment Policy environments: or ZOSMF_ENVIRONMENTS (JSON) · default via ZOSMF_ENV Named systems (DEV/TEST/UAT/PROD, LPARs) behind one server. Every tool takes an environment argument; per-environment readOnly (e.g. PROD), allowedRoles, per-user environment restrictions, and per-environment credentials with cached sessions. list_environments shows the targets.
Policy-as-code & RBAC SECURITY_POLICY_FILE=policy.yaml Roles → tool allow/deny globs, dataset/USS patterns, per-role read-only and change-ticket rules, read caps. Users → roles per environment; unmapped users get the default role or fail closed. Role inheritance with fail-safe readOnly accumulation.
Audit & SIEM SECURITY_AUDIT_FILE · SECURITY_AUDIT_SPLUNK_URL/_TOKEN · SECURITY_AUDIT_WEBHOOK_URL · SECURITY_AUDIT_OTLP_URL One JSON record per call: correlation id, user, MCP client, environment, tool, redacted arguments, outcome, duration, result size. Batched, best-effort export — a dead collector never blocks a call. SHA-256 hash chain makes the stream tamper-evident: npm run verify:audit detects any edit, deletion, or reordering.
Data protection SECURITY_DATA_PROTECTION=true (default) · SECURITY_REDACTION_RULES · SECURITY_REDACTION_STYLE · policy classifications: SSNs, credit cards (Luhn-validated), emails, secrets (PASSWORD=, api_key:), JWTs, and private keys masked in job output and dataset/USS reads, with an explicit [data protection: …] footer. Classifications add per-resource rule overrides, line caps, head/tail sampling, and role-gated access.
Policy file (roles · users · environments · classifications)
version: 1
defaults:
  role: viewer
  environment: dev
environments:
  prod:
    host: prod.zosmf.example.com
    password: ${env:ZOSMF_PROD_PASSWORD}
    readOnly: true                 # PROD is read-only
    allowedRoles: [operator, sre]
roles:
  viewer:
    tools: { allow: ["list_*", "get_*", "read_*", "search_*"] }
    readOnly: true
  operator:
    inherits: viewer
    readOnly: false                # explicit — parents are read-only
    datasets: { allow: ["PROD.**"] }
    changeTicketPattern: "CHG[0-9]{6}"
users:
  - username: BOB
    roles: [operator]
    environments: [dev, test, prod]
dataProtection:
  classifications:
    - name: pci-cardholder
      datasets: ["PROD.CARDS.**"]
      redact: [credit_card, ssn]
      maxLines: 200
      sample: { head: 100, tail: 25 }
Identity resolution: the acting user comes from the SSE X-MCP-User header (gateway deployments where an authenticating proxy injects it), ZOSMF_USER_ID, or the service account. Check the effective policy anytime by asking the agent to run whoami.
Pilot checklist: dedicated service account · PassTicket/PTKTDATA setup for end-user identity · secrets in vault · VPN/network to z/OSMF · verify_zosmf_connection · security_posture_summary · start with SECURITY_READ_ONLY=true and SECURITY_JCL_SCAN=true · enable SECURITY_AUDIT_FILE (or a SIEM sink) from day one · put roles and environments in SECURITY_POLICY_FILE rather than env-var lists · verify the trail with npm run verify:audit.
